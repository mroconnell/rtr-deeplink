# Resolver database migrations (Alembic)

Adopted 2026-08-10, mirroring `archive/alembic/`'s existing setup and
conventions exactly (same `env.py` shape, same `script.py.mako`, same
per-command usage) -- for the same underlying reason: `Base.metadata.
create_all()` can only ever *add new tables*, it can't alter an
existing one. `app/db` had never hit that wall before (every past change
was a brand-new table -- `MeetingResolution`, `ProblemReport`) until the
durable-Archive-push-tracking fix needed two new columns
(`archive_pushed_at`, `archive_push_attempts`) on the already-live
`meeting_resolutions` table. Deploying that change broke `/admin/stats`
in production (`get_stats()`'s full-table scan touches the new columns
on every row, failing with "column does not exist") until a one-off
manual `ALTER TABLE` fixed it live via Render's shell -- see
`BACKLOG_DONE.md`'s 2026-08-10 entry for the full incident. This exists
so the next `app/db` schema change doesn't need another live incident to
catch it.

**As of 2026-08-21 `create_all()` no longer runs on Postgres at all**
(`app/db/engine.py`'s `init_models()` returns early when the dialect is
`postgresql`, matching `archive/db/engine.py`) -- Alembic is the only
thing that may write production's schema, and CI runs `alembic check`
(models vs. a fresh migration-built SQLite) on every PR. The one-time
production step below is what still has to happen before
`render.yaml`'s `preDeployCommand` can run `alembic upgrade head`
automatically here the way it already does for the Archive.

`env.py` points `target_metadata` at the real models
(`app.db.models.Base.metadata`) and reads the real `DATABASE_URL`
resolution from `app.db.engine` -- there's no separate URL to keep in
sync in `alembic.ini`, dev/test/prod all naturally point at whichever
database the app itself would use.

## Creating a new migration

After changing a model in `app/db/models.py`:

```bash
cd app
alembic revision --autogenerate -m "add priority column to meeting_resolutions"
```

Autogenerate diffs the real models against whatever the target database
currently looks like -- **always review the generated file by hand**
before committing it (autogenerate is a good first draft, not a
guarantee: it can miss things like column renames, which it sees as a
drop-and-add instead, and check constraints/server-side defaults
sometimes need a manual touch-up).

## Applying migrations

```bash
cd app
alembic upgrade head
```

Run this against local dev/test databases freely. **Do not run this
against the production database without a real, deliberate decision to
do so** -- see the one-time adoption step below first.

## One-time step needed before this is usable in production

The very first migration in this history (`ee8f7ff76fb3`,
`..._baseline_schema.py`) `CREATE TABLE`s both existing tables
(`meeting_resolutions`, `problem_reports`, including the two new
`archive_pushed_at`/`archive_push_attempts` columns) from scratch, since
it was generated by diffing the real models against a genuinely empty
database.

**Production is in an unusual state, not the "never touched" state
`archive/alembic` started from**: the incident that prompted adopting
Alembic here *also already fixed* production's real schema by hand (the
one-off `ALTER TABLE ... ADD COLUMN` run live on 2026-08-10), so as of
that date production's actual columns matched this baseline migration's
`upgrade()` exactly, confirmed via `GET /admin/stats` returning
`pending_archive_pushes` cleanly. What that *doesn't* tell you is
anything about the second revision, `a9207c0eb761` (2026-08-15), which
adds `meeting_resolutions.jurisdiction_confidence` -- that column has
never been confirmed present in production either way. Read the runbook
below rather than assuming.

**Never stamp the word `head` here.** Head today is `a9207c0eb761`, not
the baseline -- and the whole point is that `head` moves. An earlier
version of this repo's docs (`BACKLOG.md`, `render.yaml`'s comment) said
"`alembic stamp head`"; that was written 2026-08-10 when the baseline
*was* head, and it silently became wrong the moment `a9207c0eb761`
landed on 08-15. Stamping `head` now would tell Alembic production has
`jurisdiction_confidence` whether or not it actually does -- the exact
shape of the 2026-08-09 Archive incident (`archive/alembic/README.md`:
"'head' isn't a fixed name"). **Always stamp a specific revision id.**

### The runbook (one time, on the `rtr-deeplink` service's Render shell)

**Step 1 -- read production's real schema first, before running any
Alembic command.** `GET /admin/schema-info` on this service (added
2026-08-21, the resolver's port of the Archive's
`/internal/schema-info`) answers both questions in one call, from
anywhere, without shell access:

```bash
curl -sS -H "Authorization: Bearer $ADMIN_STATS_TOKEN" \
  https://redtaperecordings.com/admin/schema-info | python3 -m json.tool
```

Two fields matter:

- `actual_columns.meeting_resolutions` -- **does it contain
  `jurisdiction_confidence`?** (`mismatched_tables` being empty means
  yes, plus everything else lines up too.)
- `alembic_version` -- `null` means the table exists but holds no row;
  the field is simply absent-as-null if the table doesn't exist at all.
  A 2026-08-11 `information_schema` query (BACKLOG_DONE.md) found an
  `alembic_version` table already present on this service's Postgres,
  so **do not assume "expect empty"** -- read the real value.

**Step 2 -- branch on what you actually saw.** Then, on the Render
shell for `rtr-deeplink` (the resolver, *not* the archive):

```bash
cd app
alembic current   # ALWAYS run this, and read the output
```

| `alembic current` prints | `jurisdiction_confidence` present? | Do this |
| --- | --- | --- |
| `a9207c0eb761 (head)` | (either) | **Nothing.** Already done; go to step 3. |
| nothing / empty | **yes** | `alembic stamp a9207c0eb761` |
| nothing / empty | **no** | `alembic upgrade head` -- this runs real DDL, see the warning below |
| `ee8f7ff76fb3` | **yes** | `alembic stamp a9207c0eb761` |
| `ee8f7ff76fb3` | **no** | `alembic upgrade head` (applies just `a9207c0eb761`'s `ADD COLUMN`) |
| anything else | (either) | **Stop.** Don't stamp, don't upgrade -- report what it printed. |

⚠️ **The "empty + column missing" row is the one that needs care.** With
an empty history, `alembic upgrade head` starts from the baseline, whose
`upgrade()` `CREATE TABLE`s `meeting_resolutions` and `problem_reports`
-- tables that already exist -- so it will fail with a "table already
exists" error rather than adding the column. In that case do it in two
moves instead: `alembic stamp ee8f7ff76fb3` (tell it the baseline is
already there, no DDL), *then* `alembic upgrade head` (which now only
runs `a9207c0eb761`'s single `ADD COLUMN`). The failure is loud and
harmless either way -- nothing is half-applied -- but the two-move
version is what actually works.

Then confirm, in both places:

```bash
alembic current   # must now print a9207c0eb761 (head)
```

...and re-run the `/admin/schema-info` curl: `schema_matches_models`
should be `true` and `mismatched_tables` `[]`.

**Step 3 -- only after `alembic current` prints `a9207c0eb761 (head)`,
enable the automatic migration on deploy** by uncommenting/adding
`preDeployCommand: cd app && alembic upgrade head` on the
`rtr-deeplink` service in `render.yaml`. Doing this *before* step 2
breaks the very next deploy (an unstamped history means the baseline
`CREATE TABLE`s run against live tables and fail, cancelling the
deploy). After it, the Archive's proven pattern applies here too: the
schema lands before the new build serves traffic, and a failing
migration cancels the deploy and leaves the old build running.

### If `jurisdiction_confidence` turns out to be missing in production

That isn't just a migration chore -- it means a live, silent
degradation dating to 2026-08-15. `app/db/crud.py`'s `log_resolution()`
sets `jurisdiction_confidence=` on every insert, and `app/main.py` calls
it exclusively through `safe()`, which swallows the exception -- so
**every** reporting-log row (and therefore the resolve cache
`get_cached_resolution()` reads from) would have been failing to write
since then, invisibly. `GET /admin/stats` would also 503: `get_stats()`
does `select(MeetingResolution)`, loading the full entity including the
missing column. If `/admin/stats`
currently returns cleanly, that is itself decent evidence the column
*is* there; `/admin/schema-info` is the direct confirmation.

Verified locally (2026-08-10): `alembic upgrade head` against an empty
SQLite database produces a schema that diffs identical to `create_all()`'s
(only difference: the `alembic_version` bookkeeping table itself, plus a
cosmetic `(CURRENT_TIMESTAMP)` vs `CURRENT_TIMESTAMP` default-clause
rendering difference SQLite's own introspection reports either way, same
as `archive/alembic` already documented); `alembic downgrade base`
cleanly drops both tables back out, leaving only `alembic_version`.
