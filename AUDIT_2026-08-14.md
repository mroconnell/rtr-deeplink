# App-wide audit — Red Tape Recordings

**Date:** 2026-08-14
**Scope:** industry best practices & resource management, per `BACKLOG.md`'s
"App-wide audit" section (scoped 2026-08-14, for Cowork handoff).
**Method:** read-only pass over `rtr-deeplink` and `rtr-business` at commit
`bf3ef7f`, plus live checks against redtaperecordings.com. Every finding
below cites file:line or a live observation. Where I could not verify from
the repo, the finding is marked **UNVERIFIED** with the exact check that
would resolve it.

---

## Verdict

The engineering practice here is better than the backlog section gives it
credit for. Tests are hermetic, migrations use real tooling, failures are
documented honestly rather than sanded off, rate limiting exists, and the
resolve log already captures more product signal than the "no analytics"
framing suggests. What's missing is **automation around that practice** —
nearly every safeguard is a discipline someone has to remember to exercise,
and there is no machine enforcing any of it.

Two findings are new and neither was on the backlog's list:

1. **`robots.txt` is blocking `/meetings`** — the Archive browse/search hub
   — because `Disallow: /meeting` is a prefix match. That page is
   simultaneously listed in the sitemap. This is a 15-minute fix that
   directly undercuts the discoverability work already underway.
2. **`/api/resolve` will fetch any URL you give it**, including private and
   link-local addresses, with redirects followed and a headless browser
   escalation enabled in production.

**Recommendation:** do the Batch-1 list at the bottom (about half a day,
mostly config) before the outreach campaign starts, then the SSRF guard.
Everything else can wait. Do *not* start with the instrumentation buildout
— the server-side resolve log already answers more than expected, and the
cheapest measurement win is a UTM convention you can adopt today with no
code at all.

## Findings, ranked

### 1. `robots.txt` blocks the Archive's own browse/search hub — HIGH, confirmed

`app/main.py:1116-1119` emits `Disallow: /meeting`. robots.txt matching is
**prefix-based**, so this also disallows `/meetings` — the Archive's search
and browse page (`archive/main.py:588`), which is explicitly listed as an
indexable static path in the sitemap (`archive/main.py:667`,
`_SITEMAP_STATIC_PATHS = ["/", "/about", "/coverage", "/meetings"]`).

Verified live: fetching `https://redtaperecordings.com/meetings` returns a
robots-disallowed error, while `/`, `/about`, and `/robots.txt` fetch fine.
So the site is currently telling crawlers to index a page it also tells
them not to crawl.

The comment above the directive shows the intent was only to exclude the
ephemeral `/meeting?url=…` resolver page. The `/m/{slug}` permanent pages
are unaffected — but `/meetings` is the hub that links to them, which is
exactly the kind of internal-linking surface that helps the `/m/` pages get
found.

**Fix:** replace with two lines — `Disallow: /meeting$` and `Disallow:
/meeting?` (Google and Bing both support `$` anchoring and query-string
matching). Then re-submit the sitemap in Search Console. **~15 minutes.**

### 2. `/api/resolve` fetches arbitrary URLs with no destination guard — HIGH, confirmed

`ResolveRequest.url` is a bare `str` with no validation (`app/main.py:113-114`).
Unknown hosts fall through to the generic fallback, which does
`session.get(url, allow_redirects=True, …)` (`app/platforms/generic_fallback.py:481-483`)
with no scheme allowlist, no private/link-local IP rejection, no redirect-target
re-validation, and no response-size cap. `GENERIC_FALLBACK_HEADLESS=1` is
enabled in production (commit `c135c2b`), so a real browser will also load
whatever it's pointed at.

**Failure scenario:** an anonymous POST with
`http://169.254.169.254/latest/meta-data/…` or an internal Render service
hostname causes the app to fetch it from inside the network. Response
content and error text can come back to the caller in the resolve payload.
The 20/min rate limit caps volume, not the first request.

**Fix:** validate in one place before dispatch — scheme in `{http, https}`,
resolve the hostname and reject private/loopback/link-local ranges, cap
redirects and re-check each hop, cap response bytes. **2-4 hours**, one
helper plus tests, and it protects every adapter at once.

### 3. No automated test gate; push to `main` auto-deploys — HIGH, confirmed

`.github/workflows/` contains only two `curl` cron jobs; neither checks out
the repo or runs `pytest` (658 test functions across 68 files) or `npm
test`. `render.yaml:1-10` documents that a Blueprint sync fires on every
push to `main`, and no `autoDeploy: false` or `preDeployCommand` exists.
The landing path in `CLAUDE.md:196-198` is `gh pr merge --squash` with no
required check.

The suite's own stated purpose (`CLAUDE.md:146-149`) is to catch silent
regressions *between sessions* — but nothing runs it between sessions.

Cheap here because the suite is fully hermetic: `tests/conftest.py:13-30`
pins a temp SQLite DB, HTTP is mocked, Playwright is monkeypatched. CI
needs no network, no Postgres, no browser install. Pin it to `3.12.3` to
match production (`render.yaml:55-56`); local bytecode shows dev is running
3.13.

**Fix:** one `test.yml` workflow + GitHub branch protection. **~1 hour.**

### 4. The health check cannot detect a broken deploy — HIGH, confirmed

`render.yaml:47,128` point at `/api/health`, and both implementations
return a static `{"status": "ok"}` (`app/main.py:268-270`,
`archive/main.py:109-111`) with no DB touch. In the 2026-08-09 incident the
app was failing *every* query on a missing column — a process in that state
still returns `ok`, so Render's deploy gate goes green.

**Fix:** `SELECT 1` in the health handler, 503 on failure. **1-2 hours.**

### 5. Nothing tells you production broke — HIGH, confirmed

No Sentry/Rollbar/uptime monitoring anywhere; the only acknowledgement is an
untriaged idea at `CLAUDE_BACKLOG.md:28-31` ("production exceptions
currently only surface if someone happens to check Render logs"). The daily
digest degrades silently by design — `app/reporting.py:53-60` lets one
metric fail without blanking the others, so the workflow's
`curl --fail-with-body` sees HTTP 200 on a partly-broken report.

For a product whose entire promise is "this link still works when a
journalist clicks it in six months," the current worst-case detection
latency is *someone emails Ryan*.

**Fix:** Sentry free tier on both services (1-2 hrs) + an external uptime
check against a real resolve path, not `/api/health` (30 min).

### 6. Migrations can't keep up with deploys — HIGH, confirmed, recurring

Alembic exists for both services but nothing runs it: `render.yaml:40,126`
are `pip install` only. `archive/alembic/README.md:213` states migrations
must be run "deliberately, by a person, never automatically." Meanwhile
`Base.metadata.create_all()` runs unconditionally at startup
(`app/db/engine.py:36-40`, `archive/db/engine.py:39-57`), which silently
masks any add-a-table migration so `alembic_version` falls behind reality —
the mechanism behind three documented incidents (2026-08-09, 08-10, 08-13;
`archive/alembic/README.md:198-291`).

Code ships automatically; the matching `ALTER TABLE` waits for a human. That
gap is unbounded.

**Fix, in order:** gate `create_all()` to dev/SQLite only (1-2 hrs), do a
one-time `alembic current` reconciliation on both prod services, *then* add
a `preDeployCommand` running `alembic upgrade head` (2-3 hrs). Automating
before reconciling will fail on the first run.

### 7. No privacy policy or terms — MEDIUM, confirmed

`app/templates/` contains no privacy or terms template, and no route serves
one (`app/main.py:1022-1131`). The site meanwhile loads Google Analytics
(`app/templates/base.html:17-22`), collects emails via newsletter signup and
transcription requests, and runs Clerk accounts storing `clerk_user_id`
(`archive/db/models.py:193`).

This is already tracked in `rtr-business/TASKS.md`, so it isn't news — but
it's worth restating that a California LLC running analytics cookies and an
email list with no posted privacy policy is the kind of gap that is trivial
to fix now and awkward to fix after a journalist or a nonprofit's counsel
asks about it. *Not legal advice — have a lawyer look at whatever you post.*

### 8. Instrumentation: the gap is attribution, not events — MEDIUM, confirmed

What exists: five GA events (above) and a rich server-side resolve log.
What's missing that actually matters for the campaign starting now:

- **No outreach attribution.** If you send 10 personalized deep links
  tomorrow, nothing distinguishes those visits from organic ones.
- **No resolve-outcome event.** GA sees `submit_meeting_url` but never
  learns whether the resolve succeeded, so the funnel's most important step
  is invisible client-side (it *is* in `MeetingResolution.status`, just not
  joinable to a session).
- **No engagement event.** No video-play, no transcript-click, no
  archive-page-view — so "did they actually use it" is unanswerable.

**The cheapest thing that works, and it needs no code:** append
`?utm_source=outreach&utm_campaign=first10&utm_content=<recipient-slug>` to
every personalized link you send. GA segments on that automatically. Do
this before the first email goes out — it is unrecoverable afterward.

**Then, one afternoon of code:** fire `resolve_result` with
`{status, platform}` from the resolve response handler, and `video_play` +
`transcript_seek` from `player.js` (which already has `trackEvent` in
scope). Those three events plus UTMs answer "who did I reach, did it work
for them, did they use it."

### 9. Cost inventory — MEDIUM, partially unverified

From `render.yaml` plus Render's published pricing: resolver `starter`
($7/mo), Archive `starter` ($7/mo), worker `standard` ($25/mo) = **$39/mo
confirmed**, plus domain, Resend, and Clerk (both plausibly on free tiers —
unconfirmed).

**The real finding is the databases.** `render.yaml` has no `databases:`
block at all, so both Postgres instances live entirely outside the tracked
Blueprint. Render's free Postgres tier has a **30-day limit** — if either
instance is on it, the Archive's permanent pages are on a clock. Nobody has
checked. This is the single highest-consequence unknown in the audit and it
takes five minutes to resolve.

Related, same root cause: `render.yaml:1-10` records a real incident where
a push silently reverted manually-set paid plans back to `free`. A future
push could do it again, reintroducing the cold starts that hurt crawl
health on `/m/*`.

### 10. Dependencies unpinned, no vulnerability scanning — MEDIUM, confirmed

Every entry in all three requirements files uses `>=` with no upper bound
and no lockfile, while `render.yaml:40,126` reinstalls on every deploy — so
two deploys of identical source can install different versions. No
Dependabot config, no `pip-audit`. (`yt-dlp` being loose is a deliberate,
documented choice at `CLAUDE.md:128-136` and should stay that way.)

**Fix:** `pip-compile` a lockfile per service, keep `yt-dlp` and
`faster-whisper` loose with a comment, then turn on Dependabot. **2-3 hrs.**

### 11. Admin token travels in the URL query string — MEDIUM, confirmed

`daily-report.yml:38` and `send-search-alerts.yml:37` both build
`…?token=${{ secrets.ADMIN_STATS_TOKEN }}`. GitHub masks it in Actions logs;
Render's request logs do not. The Archive already does this correctly with
`Authorization: Bearer` (`archive/main.py:100-106`) — copy that pattern.
This repo has already had one token-exposure incident requiring rotation in
three places (`CLAUDE.md:206-214`). **~45 min.**

### 12. No linter/formatter, and `.claude/` is tracked — LOW, confirmed

No ruff/black/mypy/pre-commit config anywhere. Given the documented pattern
of multiple agent sessions editing one tree the same day
(`CLAUDE.md:182-205`), a formatter is mostly about keeping `git pull
--rebase` clean. Separately, `.gitignore` correctly covers `.env`, `*.db`,
and `.venv` — but not `.claude/`, so `settings.local.json` (which
pre-approves `git push` for every session) and `launch.json` (which
hardcodes `/Users/mroconnell/…`) are shared with every clone. **Add
`.claude/` to `.gitignore`: 2 minutes.**

### Things that are genuinely fine

Worth saying explicitly, since the backlog section leans pessimistic:
rate limiting is real and sensibly tiered; `secrets.compare_digest` is used
for both admin and ingest tokens rather than `==`; the Archive's internal
endpoints return 404 (not 403) on bad auth, which is the right choice; the
`/internal/schema-info` endpoint was purpose-built to prevent a repeat
incident and is a genuinely good piece of operational engineering; the test
suite is hermetic and fast; and `aria-` usage across templates holds up on
inspection. The accessibility "positive finding" in the backlog is real,
though still unverified by any automated tool.

## External checklist — five things only you can check

Each is a dashboard look, not a code change. The first one matters most.

1. **Render → Postgres.** What plan is each of the two databases on? If
   either says **free**, it expires 30 days from creation — find out when.
   Also: are automated backups / point-in-time recovery on, and what's the
   retention window? *(Resolves the audit's biggest unknown.)*
2. **Render → each of the three services.** Does the plan shown match
   `render.yaml` (`starter`, `starter`, `standard`)? A past push silently
   reverted these. Also grab the actual current month's bill so the $39/mo
   estimate can be replaced with a real number.
3. **Google Analytics.** Is the property actually receiving events — and do
   you see `submit_meeting_url` and `copy_link_to_time` in the last 30
   days? The code is wired; whether data is landing is unverified.
4. **Resend + Clerk.** What plan is each on, what does each cost, and how
   close are you to the free-tier ceiling? (Needed to finish the cost
   inventory.)
5. **The search-alert cron.** `send-search-alerts.yml` runs daily and has
   never been human-verified firing for real. Check a recent Actions run's
   output and confirm at least one alert email actually sent.

4. Add `.claude/` to `.gitignore` (2 min).

**Batch 3 — when there's a quiet day:**

10. `create_all()` gating, then Alembic reconciliation, then
