# Archive database migrations (Alembic)

Adopted 2026-08-09 as the real fix for a wall this repo hit three separate
times: `Base.metadata.create_all()` (still run on every startup, see
`archive/db/engine.py`'s `init_models()`) can only ever *add new tables* --
it can't alter an existing one. That's fine for a brand-new table
(`TranscriptionJob` shipped this way with zero migration tooling), but not
for changing a table that's already live in production with real rows in
it -- the job-priority column and the materialized search column both hit
this wall (see `BACKLOG.md`/`BACKLOG_DONE.md`).

`env.py` points `target_metadata` at the real models
(`archive.db.models.Base.metadata`) and reads the real `DATABASE_URL`
resolution from `archive.db.engine` -- there's no separate URL to keep in
sync in `alembic.ini`, dev/test/prod all naturally point at whichever
database the app itself would use.

## Creating a new migration

After changing a model in `archive/db/models.py`:

```bash
cd archive
alembic revision --autogenerate -m "add priority column to transcription_jobs"
```

Autogenerate diffs the real models against whatever the target database
currently looks like -- **always review the generated file by hand**
before committing it (autogenerate is a good first draft, not a
guarantee: it can miss things like column renames, which it sees as a
drop-and-add instead, and check constraints/server-side defaults
sometimes need a manual touch-up).

## Applying migrations

```bash
cd archive
alembic upgrade head
```

Run this against local dev/test databases freely. **Do not run this
against the production database without a real, deliberate decision to
do so** -- see the one-time adoption step below first.

## One-time step needed before this is usable in production

The very first migration in this history (`..._baseline_schema.py`)
`CREATE TABLE`s all four existing tables from scratch, since it was
generated by diffing the real models against a genuinely empty database.
Production already has all four tables (created by `create_all()` over
this repo's life so far, real rows already in them) -- running
`alembic upgrade head` against it as-is would fail on `CREATE TABLE`
against tables that already exist.

Instead, production needs to be told "you're already at this point in the
migration history, don't actually run it" -- Alembic's `stamp` command
does exactly that: it writes the revision id into a new `alembic_version`
table without touching any other table.

**This needs to be run once, deliberately, by whoever has production
`DATABASE_URL` access** (this session doesn't) -- from a real shell with
that env var set to the production Postgres URL:

```bash
cd archive
alembic stamp head
```

Verified locally (2026-08-09, not yet run against production): a fresh
`alembic upgrade head` against an empty SQLite database creates a schema
that diffs identical to `create_all()`'s (only difference: the
`alembic_version` bookkeeping table itself, plus a cosmetic
`(CURRENT_TIMESTAMP)` vs `CURRENT_TIMESTAMP` default-clause rendering
difference SQLite's own introspection reports either way); `alembic
downgrade base` cleanly drops everything back out. Not yet verified
against a real Postgres database specifically -- worth a real check
there too before the first `stamp head` against production, since
Postgres's own type/default rendering can differ from SQLite's.
